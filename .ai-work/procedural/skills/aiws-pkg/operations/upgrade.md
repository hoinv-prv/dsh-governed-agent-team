# aiws-pkg — operation: upgrade

> Operation of the `aiws-pkg` domain skill (consolidated by CR-AIWS-2026-07-025; former standalone skill — see `product/rename_map.json`). Content preserved verbatim; every gate herein stays binding.


## Purpose
Upgrade payload sections of an existing AIWS installation (skills, tooling,
wiki_guidelines, etc.) from a newer install package.
Never touches Truth files or project runtime.

## Inputs
- `package_path` (required) — absolute path to the new install package folder
- `project_root` (optional) — default: current directory
- `sections` (required) — which sections to upgrade (all / by number / `changed`)

## Flow
1. Self-update check — if package has a newer version of this skill, offer to update it first
2. **Version detection — `install_templates/VERSION` là THẨM QUYỀN** (CR-AIWS-2026-08-089 C3).
   - Đọc `.ai-work/install_templates/VERSION` của target (stamp lúc build, đến theo section copy) và so với `VERSION` trong package. Đây là nguồn duy nhất `compose_aiws_rules.py` chấp nhận.
   - **`.aiws-version` KHÔNG phải nguồn thẩm quyền.** Nó chỉ là ghi chú do **bước 7** của chính lệnh upgrade viết, nên một dự án **cài mới rồi nâng cấp lần đầu KHÔNG có file này** (`compose_aiws_rules.py`: *"install/quick-install do not write that file"*). Có thì đọc tham khảo; vắng **không** phải lỗi.
   - **Thiếu CẢ HAI nguồn ⇒ DỪNG, hỏi HUMAN** (DP-089-D). Không suy ra "chắc là bản cũ" rồi apply cả cây — đó là ghi đè dựa trên phỏng đoán. Cùng khuôn `account_id resolve` (CR-AIWS-2026-08-076): mơ hồ thì rc≠0, không tự chọn.
   - **Hai package có thể mang CÙNG số version** (đã xảy ra: v1.2.0 bản 15-08 và 17-08). Khi số trùng mà bạn ngờ nội dung khác, đừng tin số — đo bằng bước 4: `apply-list = 0` mới thật sự là đã mới nhất.
3. Section selection — show section status (ADD / UPDATE / UNCHANGED); ask user to select
4. **Diff analysis — per-file status (ADD / UPDATE / UNCHANGED / REMOVED) for the selected sections.** Run it; do not eyeball it (CR-AIWS-2026-08-088):
   `py .ai-work/tooling/diff_payload_tree.py --package <pkg> --target . [--sections a,b]`
   — `--status ADD,UPDATE` prints exactly the apply-list step 5 copies · `--format jsonl` to script it · `--strict-eol` compares bytes instead of the default EOL-insensitive view (default is EOL-insensitive on purpose: a file differing only in line endings must not be copied, or the upgrade manufactures the EOL churn 7b/CR-073 C1 just removed).
   **The package `CHANGELOG.md` cannot answer this question.** Its counts are **package-vs-package** — the delta from the previous release to this one. A project that skipped a release, or edited a file after installing, has a different delta into ITS tree. Measured case (IR-2026-08-15 F8): CHANGELOG said 119 new / 78 updated / 55 removed; the real delta into the target was **147 ADD / 173 UPDATE**.
   The tool is **read-only** — it reports, step 5 copies. `wiki_source_profiles` rows come flagged **MERGE-only**: never copy-overwrite them (step 7 exception, CR-AIWS-2026-06-047). `payload/aiws_wiki_index/` is not compared here — step 7b owns it.
5. Temp-first: copy ADD/UPDATE files to `.aiws-upgrade.tmp` — do not touch originals yet
6. Show upgrade report to user; ask for confirmation
7. Apply — copy temp files to destinations; delete temp files; write `.aiws-version`. **Exception — `wiki_source_profiles`:** project-owned → do NOT copy-overwrite; **MERGE** via `py .ai-work/tooling/merge_wiki_source_profiles.py --from <pkg>/payload/wiki_source_profiles --into .ai-work/wiki_sources/profiles --apply` (adds only missing canonical top-level keys; preserves the project's profiles + `extra_stopwords`; never writes `project_stopwords.yml`) — CR-AIWS-2026-06-047
7b. AIWS wiki refresh (CR-040 + CR-AIWS-2026-08-064 + CR-AIWS-2026-08-073 C1) — if the new package ships `payload/aiws_wiki/`, refresh ONLY the `aiws` namespace with a **PRECISE APPLY**, same discipline as step 5: write a meta **only when its content differs** (compare EOL-normalized), and leave byte-identical metas untouched. Do NOT rmtree-and-copy the bundle — a wholesale replace rewrites every meta, so a run whose real delta is a few dozen files shows up as the whole bundle churning (payload ships LF; a CRLF tree then reports every file as changed) and buries the actual diff. `build_preset_wiki.py` does this for you (`py .ai-work/tooling/build_preset_wiki.py --target .`); if you copy by hand, compare before writing. Then copy the pre-built `payload/aiws_wiki_index/{index.aiws.jsonl,relations.aiws.jsonl}` into `.ai-work/wiki_sources/`. NEVER touch the project's own `index.jsonl` / `relations.jsonl` / `meta/` (domain wiki).
7c. **Rename migration (CR-AIWS-2026-07-020)** — if the package ships `payload/tooling/rename_map.json` (installs to `.ai-work/tooling/rename_map.json`), read it; for each `renames[].old` whose OLD-named skill/command folder still exists AND whose NEW name was installed, **delete the renamed-away OLD folder** — temp-first + HUMAN-confirmed (sanctioned scoped exception to "never auto-delete"; map-listed renames only). Entries with `special: keep_old_as_deprecation_pointer` (e.g. `aiws-pkg upgrade`) are KEPT one transition release. Then run `py .ai-work/tooling/check_aiws_upgrade.py --verify`: with the shipped rename_map it recognizes renames instead of flagging "deleted by upgrade".
7c-bis. **Desk-dir migration `agents/instances/` → `agents/task_desks/` (CR-AIWS-2026-08-074 C1)** — P2 (CR-AIWS-2026-08-006) renamed the desk root and shipped a **dual-read** as the transition; nothing ever performed the transition, so a project installed before P2 stays on the legacy branch forever while every guide teaches the new name.
    **Why this is not cosmetic.** `run_agent.py` resolves `TASK_DESKS = _DESKS_NEW if _DESKS_NEW.is_dir() else _DESKS_OLD` and `_all_instances()` iterates that **one** directory — there is no union. The switch condition is that `agents/task_desks/` **EXISTS**, not that it holds desks. So on a legacy tree, creating one desk under `agents/task_desks/` (exactly what `INSTANCE_INITIALIZATION_GUIDE.md` tells you to do) makes **every** desk under `agents/instances/` invisible to `list` / `run` / `status` / `upgrade` at once — no error, no warning. The desks are still on disk; their `memory/`, `run_index.jsonl`, `training/` and `tools/` are simply unreachable through the tooling, which for a user is indistinguishable from losing them.
    **Preconditions — refuse, do not guess:** if **both** `agents/instances/` and `agents/task_desks/` exist **and both hold desks** → **STOP and ask the HUMAN**; never merge automatically (two desks could carry the same id). If `agents/task_desks/` exists and is **empty** while `agents/instances/` holds desks → that is the trap already sprung: STOP, report it, and offer this migration after the HUMAN removes the empty directory.
    **What the migration MUST do** (this alone restores resolution): rename the directory `agents/instances/` → `agents/task_desks/`. **Temp-first + HUMAN confirm**, same controlled-exception discipline as 7c.
    **What it SHOULD also do** (completes P2; dual-read still covers a desk if skipped): per desk, `instance.yaml` → `desk.yaml`.
    **What it must NOT touch:** desk content — `memory/`, `run_index.jsonl`, `training/`, `tools/`, `workspace/`, `context/`, `process/`, `blueprint_ref.yaml`, `changelog.md`. `instance_readme.md` is **not resolved by any tooling** (grep: 0 hits) — leave it; renaming it buys nothing and touches a file a HUMAN may have edited. `.blueprint_snapshot/` may be left as-is: `_snapshot_dir()` dual-reads it, and renaming it silently rewrites the drift baseline.
    **Idempotent:** already on `task_desks/` (or no desk dir at all) → **no-op**, report and continue. Re-running after a completed migration must change nothing.
    **Verify after:** `py .ai-work/agents/tooling/run_agent.py list` must show **the same desk count as before** the migration. Count first, compare after — a migration that silently drops a desk looks exactly like a successful one.
7d. **Referrer-scan after rename migration (CR-AIWS-2026-07-033 T4 / H-02; scope INVERTED by CR-AIWS-2026-08-087)** — after 7c deletes, grep each just-deleted OLD name across **every tracked file EXCEPT the zones listed below**.
    **Scope is "everywhere but the forbidden zones", not "the places we thought of."** The old wording named a fixed include-list (`truth/` top-level, `CLAUDE*.md`, `.claude/`, `.ai-work/procedural/`, `.ai-work/aip/templates/`). A target project can stand up a skill surface AIWS has no name for: `.agents/skills/` — Codex' discovery dir, declared in that project's own `AGENTS.md` — was a real one, and 7d returned **0 hit while a genuinely broken link was sitting in it** (IR-2026-08-15 F7). Adding that one name to the list would only postpone the same miss to the next surface; AIWS cannot know in advance what a project will build.
    **Enumerate with `git ls-files`** — tracked files only (DP-087-B = a). Untracked files are the project's build/scratch output: scanning them is noise, and it is also how you wander into a human-managed area nobody has declared yet.
    **EXCLUDE absolutely** — this is what makes the inversion safe, and it may NOT be relaxed: `temp/`, `.ai-work/logs/`, `.ai-work/wiki_sources/index.local.jsonl` and every human-managed area. Always-on rules #1 and #11 apply to the TARGET tree, so a literal "whole repo" grep would breach them.
    **Immutable zones** (`change_requests/`, `history/`, `workspaces/`, `releases/`) stay informational-tag only — old names there are **legitimate** (rename_map note: "old names remain resolvable... NOT rewritten"). Report them separately or not at all; never treat them as breakage.
    **Noise stays low because the needle is specific:** 7d greps the exact name just deleted, not a general pattern. Widening the haystack does not widen what matches.
    Any hit → **report to HUMAN as file:line + the new replacement name** (from `rename_map.json`) — **NEVER auto-edit Truth** (Truth pointing at a deleted skill silently breaks the target's gates; the warning is the fix, the edit is the HUMAN's).
7d-bis. **EOL convention seed (CR-AIWS-2026-08-073 C3)** — seed `.gitattributes` carrying `* -text` (CR-AIWS-2026-08-005) — **seed-if-absent at the project ROOT**, never overwritten. v1.2.0 shipped `check_eol_alignment.py`, whose docstring asserts this convention, without ever handing the convention to the target (IR-2026-08-15 F6). If a project declines it (has its own `.gitattributes`, or removes the seeded one), `check_eol_alignment.py` will report cross-source EOL noise — that is expected, not a bug. On upgrade this is the same create-if-missing step as install: an existing file is left alone.
7e. **Rule files (CR-AIWS-2026-08-066)** — refresh the ONE source, then re-render every wired rule file:
   (i) overwrite `.ai-work/install_templates/` (incl. the new `VERSION`) from the package (temp-first like every other UPDATE), **rồi materialise core rules** (CR-AIWS-2026-08-089 C1):
       ```
       cp .ai-work/install_templates/aiws_core_rules.md  .ai-work/AIWS.md
       ```
       **Package KHÔNG chứa file tên `AIWS.md`** — nguồn của nó là `install_templates/aiws_core_rules.md`, đúng như bước 5.1 của `install_guide.md`. Bản cũ của bước này viết *"overwrite `.ai-work/AIWS.md` from the package"*, một câu **không thi hành được**, và hệ quả là core rules của target **đóng băng ở thời điểm cài**: `--refresh` re-render từ core cũ và `--check` báo `OK` vì so với chính core cũ đó (IR-2026-08-17 F2).
       **`.ai-work/AIWS.md` là package-owned — ghi đè, KHÔNG merge.** `install_guide.md`: *"core rules (model-agnostic, package-owned — upgrade ghi đè)"*. Nội dung của dự án sống **NGOÀI** AIWS block trong file rule của từng tool, không sống trong file này (`install_templates/README.md`: *"Truth > project-owned ngoài block > nội dung trong AIWS block"*).
       **Không phải nhớ làm bằng tay:** `compose_aiws_rules.py --init/--refresh` tự materialise khi `AIWS.md` vắng **hoặc** khác template, và **báo ra** khi nó ghi đè một bản đã khác (DP-089-A). Câu lệnh trên là để bạn hiểu chuyện gì xảy ra, không phải thao tác bắt buộc.
   (ii) `py .ai-work/tooling/compose_aiws_rules.py --refresh` (dry-run — shows the diff) → HUMAN confirm → re-run with `--apply`. Refresh carries the new **adapter AND core AND version**, and touches nothing outside the AIWS block;
   (iii) a rule file **without** the marker is NOT silently skipped: if it holds hand-written AIWS rules (fingerprint `AI Work System MVP`), REPORT it to the HUMAN and offer `--migrate-legacy` (wraps the old section, keeps the project-owned parts, backs up first). Silently skipping is how a project that adopted AIWS before this mechanism would never receive another rule update;
   (iv) verify `compose_aiws_rules.py --check` → rc=0.
7f. **Project profile (CR-AIWS-2026-08-128)** — run `py .ai-work/tooling/project_profile.py init` (creates it only if this install predates the file) then `py .ai-work/tooling/project_profile.py check`. The profile is **project-owned**: an upgrade seeds it when absent and otherwise only ever REPORTS. Missing keys → offer `refresh --apply` (additive, inside the AIWS block, zero deletions). Broken invariant → **ask the HUMAN**; never fill one in. An upgrade that silently completed a config decision would be the exact failure this CR removes.
8. Post-upgrade checklist — remind user to review REMOVED files **and the 7d referrer-hit list (especially Truth hits)**, run `/aiws-lint`. **Rule files:** those carrying the AIWS block were refreshed in 7e — only the project-owned parts OUTSIDE the block (and any marker-less file reported in 7e-iii) still need a human look.

## Rules
- `wiki_source_profiles` is project-owned — **merge, never overwrite** (use `merge_wiki_source_profiles.py`); never write `project_stopwords.yml` (CR-AIWS-2026-06-047)
- never overwrite Truth files (`SOP_MASTER`, `AI_WORK_CONTRACT`)
- never touch project runtime (`workspaces/`, `aip/exec|plans|local/`, `history/`, `wiki/`)
- rule files: never write outside the `AIWS:BEGIN rules` block; never migrate a legacy file without HUMAN confirmation (CR-AIWS-2026-08-066)
- AIWS wiki refresh (CR-040 / CR-064) touches ONLY `wiki_sources/aiws_meta/` + `index.aiws.jsonl` + `relations.aiws.jsonl` (the `aiws` namespace); NEVER the project's own `wiki_sources/index.jsonl` / `relations.jsonl` / `wiki_sources/meta/` (domain wiki)
- never auto-delete REMOVED files — only notify. **Exception (CR-AIWS-2026-07-020):** renamed-away skill/command folders listed in the shipped `rename_map.json` MAY be deleted (temp-first, HUMAN-confirmed); `special` deprecation-pointer entries are kept one release
- never apply before user confirmation — temp-first is mandatory
- stop and ask on any permission or encoding error
